## 1. 概述与范围

### 1.1 定位

本文档为 FlatWire Protocol（FW）的**规范性协议设计文档**，定义线格式、交互语义与服务契约。

- FW 是**应用层协议**：不定义 TCP 连接状态机（TCP 由操作系统管理）

- TCP/UDP 共用预定义端口（默认 5400），由 SvcID/IfID 实现多路复用

- 本文档**不包含**设计动机、实现指导与测试用例。文中"必须/禁止/应"为规范性要求

- FW 面向**可信网络**，协议层不提供安全保证（见 §2）

### 1.2 设计原则

| 原则     | 说明                                                             |
| ------ | -------------------------------------------------------------- |
| 应用层协议  | 仅定义帧格式、交互语义与服务契约                                               |
| 统一端口   | TCP/UDP 共用预定义端口，由 SvcID/IfID 多路复用                              |
| 双角色节点  | 一个节点可同时作为服务端与客户端，两套状态独立维护                                      |
| 服务契约驱动 | 服务注册后自动广播 Offer；接口集合由 IDL 定义（**纯动态：运行时加载，协议栈不内置 IDL**，见 §11.1） |
| 裸字节编码  | 字段按 IDL 定义顺序裸值连续编码：无字段头、无类型标记、无结构边界；宽度与长度前缀全部由 IDL 静态确定（见 §9） |

### 1.3 超时与保活

所有时间参数统一毫秒（ms）。附录 A 为唯一参数默认值表。

| 类别       | 默认值     | 作用                                     |
| -------- | ------- | -------------------------------------- |
| 应用层响应超时  | 2000ms  | 调用的**唯一终态**判定；每次调用可单独覆盖                |
| TTL 有效期  | 4000ms  | 服务/订阅生命周期（Entry 中以秒为单位携带，见 §7.1）       |
| TCP 半帧超时 | 5000ms  | 帧接收未完成时的保护：帧头不完整关连接 / 帧头完整丢弃恢复（见 §4.1） |
| TCP 心跳超时 | 60000ms | 半开连接检测（见 §5.7）                         |

### 1.4 关键约束

- **可靠性分层**：CON/ACK 为 **UDP 专用**送达保证；TCP 由协议自身保障，不使用 CON/ACK（所有帧 TYP=NON）

- **TTL=0 延迟移除**：收到 TTL=0 后不立即删除条目，统一延迟到下一次 tick 清理（见 §7.5）

- **协议版本与服务版本独立**：VER 为传输协议版本（帧格式级），MajorVer/MinorVer 为服务版本（接口语义级）

- **`(SvcID, InstID)`** **跨节点唯一**：由部署规划保证的运行前提；协议层不提供冲突检测或仲裁（见 §3.5）

## 2. 传输层约定

TCP/UDP 共用端口 5400。传输协议按接口类型绑定（IDL 声明）：rpc/ff 默认走 TCP，event 默认走 UDP。

SD 使用 UDP 组播（224.0.1.187 / ff02::1:BB），Find 响应用 UDP 单播。**IDL 查询（GetIDL，见 §7.2）为唯一走 TCP 单播的 SD 操作**——IDL JSON 文本可达数 KB\~数十 KB，超出 UDP `max_payload_len`（1400）适用范围。

**组播部署约定**：

- 组播作用域：IPv4 224.0.1.187 为组织本地范围（TTL 默认 1，即链路本地；跨网段部署由路由器策略决定），IPv6 ff02:: 为链路本地——两侧作用域不对称，部署时以 IPv4 TTL / IPv6 hop limit 配置明确预期范围

- **单实例部署约束**：同一主机仅运行一个协议栈实例（多实例场景不在协议范围内）；`IP_MULTICAST_LOOP` 默认开启（本机组播回环）

- **启动预热**：协议栈**启动时立即发送一次 Find（空 Payload，查询所有服务）**，加速发现缓存预热——使注册/调用的 IDL 按需拉取在启动早期即可命中在线实例（见 §7.2/§11.1），无需等待首轮周期 Offer（period\_ms）

- 客户端 UDP socket 绑定**临时端口**（不绑定 5400），避免与同主机服务端进程的端口冲突；服务端地址由 SD Offer 的源地址获知，不依赖对端端口

- **组播不可用降级**：WiFi / 部分交换网络可能抑制组播。客户端可退化为对已知服务端地址周期发送单播 Find（间隔 `period`）兜底，行为与组播发现等价

**周期与 TTL**：Offer 与 Subscribe 共用同一组配置，须满足：

```
ttl >= 2 * period
```

| 参数          | 默认值（ms） |
| ----------- | ------- |
| `period_ms` | 2000    |
| `ttl_ms`    | 4000    |

> Entry 中携带的 TTL 字段以**秒**为单位（uint8，见 §7.1）；配置与超时参数一律 ms。

**最大载荷**：`max_payload_len` 定义**单帧 Payload 上限，仅适用于 UDP**（默认 **1400** 字节，可整帧装入典型以太网 MTU，避免 IP 分片）。超过时编码报错、接收方回 RST(0x23)（见 §3.8、§4.2）。

TCP 无 `max_payload_len` 限制：TCP 为流式传输，一帧可承载完整 IDL 对象（如 1MB Blob），仅受 PLB=7 的 2^56 字节理论上限与 IDL `max_payload`/字段 `max_len` 约束（见 §3.8）。协议层无分段/重组语义，"TCP 流式传输保障"指单帧承载完整对象、由 TCP 自身完成分段。

**接口级负载上限**：IDL interface 的 `max_payload` 约束该接口单帧 Payload 的字节上限，TCP/UDP 均适用；字段级 `max_len` 约束单个变长字段，两者不同名以示区分。

**协议版本（VER 字段）**：

- VER 表示传输协议版本（帧格式级），**不同 VER 即不同方案，无协商降级语义**

- VER=0：当前版本（裸字节编码，见 §9），所有实现必须支持

- **部署约束：全网协议栈必须采用同一线格式版本**（裸字节编码）。不同线格式的实现不得混部

- 发送端始终以本地支持的 VER 发送所有帧（数据帧和控制帧）

- **通信前提：双方 VER 必须相等**。VER 不一致则不可通信：

  - 组播帧（Offer / Find / Subscribe）：静默丢弃

  - 单播帧（数据帧 / 控制帧）：回 RST(0x22) 并丢弃

- 对端 VER 由 SD Offer 携带，客户端仅在 VER 相等时才认为服务可用

- FW 为一次性固化协议：VER 空间（2bit，0\~3）耗尽即终止演进，不做协商降级

**安全边界**：VER=0 **不提供鉴权、完整性、机密性**保护。MSK（见 §10）仅为载荷混淆，不是安全机制。需要安全保证的部署应由环境层提供（封闭网络、VPN、链路加密或上层安全协议）。

**字节序与扩展**：所有多字节整数统一大端序。压缩/加密/CRC 由服务契约约定，不在帧头标志。

## 3. 帧格式

### 3.1 帧整体结构

```
 +0              +1              +2              +3
 7 6 5 4 3 2 1 0 7 6 5 4 3 2 1 0 7 6 5 4 3 2 1 0 7 6 5 4 3 2 1 0
+-------+-------+-------+-------+-------+-------+-------+-------+
|CTR|REN|VER|MSK|PLB|TYP | Code |        Service ID (2B)        |
+-------+-------+-------+-------+-------+-------+-------+-------+
|      Interface ID (2B)        |  Instance ID  |   Stream ID   |
+-------+-------+-------+-------+-------+-------+-------+-------+
|                     Payload Length                            |  <- PLB 决定 Length 字段字节数
+-------+-------+-------+-------+-------+-------+-------+-------+
|                       [Masking Key (4B)]                      |  <- MSK=1 时存在
+-------+-------+-------+-------+-------+-------+-------+-------+
|                   Structured Data Fields                      |
|                   ...                                         |
+-------+-------+-------+-------+-------+-------+-------+-------+
```

固定头 8B：byte0/byte1（2B 控制头）+ SvcID/IfID（4B）+ InstID/StrmID（2B）。

解析顺序：byte0 → byte1 → SvcID → IfID → InstID → StrmID → Length（PLB>0 时）→ Mask（MSK=1 时 4B）→ Data

**Payload Length 定义**：Data Fields 字节数 + 契约级附加字段（CRC16 等）之和，**不含 Masking Key**。

控制帧（CTR=1）与数据帧（CTR=0）格式相同，仅 Code 语义不同。

### 3.2 byte0 定义

```
CTR:1 | REN:1 | VER:2 | MSK:1 | PLB:3

 76543210
 x....... CTR  是否是控制帧
 .x...... REN  重启标志（仅 CTR=1 时有效，CTR=0 时恒为 0）：
                1=发送方已重启，对端应重置该节点服务缓存
 ..xx.... VER  版本号（0=当前版本；双方必须相等，见 §2）
 ....x... MSK  是否有掩码（1 时于 Payload Length 后插入 4B XOR 密钥）
 .....xxx PLB  payload length 字段实际占用的字节数（0~7）
```

空 payload：PLB=0，无 Length 字段，帧大小最小 8B。

### 3.3 byte1 定义

```
TYP:2 | Code:6

 76543210
 xx...... TYP  传输类型（见 §3.7）
 ..xxxxxx Code  消息编码（见 §3.4）
```

### 3.4 Code 编码

| Code (CTR=0) | 语义                                                           |
| ------------ | ------------------------------------------------------------ |
| 0x00         | 空确认（TYP=ACK 时）／协议违规（TYP=RST 时）                               |
| 0x01         | Request（需响应）                                                 |
| 0x02         | Fire-Forget                                                  |
| 0x03         | Notification                                                 |
| 0x04\~0x0F   | 保留                                                           |
| 0x10\~0x1F   | 成功响应（**0x10=OK，Response 唯一成功码**，见 §5.1；0x11\~0x1F 保留，暂无使用场景） |
| 0x20\~0x2F   | 客户端错误（见 §12.1）                                               |
| 0x30\~0x3F   | 服务端错误（见 §12.1）                                               |

| Code (CTR=1) | 语义                                                                                                                      |
| ------------ | ----------------------------------------------------------------------------------------------------------------------- |
| 0x00         | 连接级控制（REN=1 时=重启通知；REN=0 时=心跳 Ping）                                                                                     |
| 0x01         | SD Offer（TTL=0 表示停止提供）                                                                                                  |
| 0x02         | SD Find                                                                                                                 |
| 0x03         | SD Subscribe（TTL=0 表示取消订阅）                                                                                              |
| 0x04         | SD GetIDL（查询服务 IDL，**仅 TCP 单播**；StrmID=客户端协议栈分配 0x01\~0x7F，触发方为协议栈内部，见 §7.2；UDP 收到 → RST(0x00)）                         |
| 0x05\~0x0F   | 保留                                                                                                                      |
| 0x10\~0x1F   | SD 成功响应（**0x10 = Subscribe 确认，订阅已建立**，见 §8.1；**0x11 = GetIDL 响应**，回显请求 StrmID，Payload=IDL JSON 全文，见 §7.2；0x12\~0x1F 保留） |
| 0x20\~0x2F   | SD 客户端错误                                                                                                                |
| 0x30\~0x3F   | SD 服务端错误                                                                                                                |

> `Code=0x00` 语义由 TYP 与 CTR 共同决定：`TYP=ACK` → 空确认；`TYP=RST` → 协议违规；`CTR=1 且 REN=0` → 心跳 Ping；`CTR=1 且 REN=1` → 重启通知。
> 控制帧 `Code=0x10`（CTR=1）与数据帧 `Code=0x10`（CTR=0，OK 响应）互不冲突——CTR 区分两个码空间。

> 错误码语义与恢复策略以 §12.1 为唯一权威表。

### 3.5 消息标识符

| 字节   | 字段     | 数据帧 (CTR=0)                                | 控制帧 (CTR=1)                                                                              |
| ---- | ------ | ------------------------------------------ | ---------------------------------------------------------------------------------------- |
| 2\~3 | SvcID  | 0x0001\~0xFFFF                             | 固定 0x0000                                                                                |
| 4\~5 | IfID   | 0x0001~~0x7FFF=rpc/ff，0x8000~~0xFFFF=event | 固定 0x0000                                                                                |
| 6    | InstID | 0x01\~0xFF                                 | 固定 0x00                                                                                  |
| 7    | StrmID | 0x01~~0x7F 客户端流 / 0x80~~0xFE 服务端流          | 0x00=连接级（REN/心跳/Offer/Find）；0x01\~0x7F=请求-响应型控制交互（Subscribe 会话 / GetIDL 查询，客户端分配，见 §7.2） |

**ID=0 通配规则**：SvcID=0x0000 / IfID=0x0000 / InstID=0x00 仅在 SD 查询/订阅场景中表示"任意/全匹配"（见 §7.2），数据帧中禁止出现。

**IfID 语义分区**：0x0001~~0x7FFF 用于 rpc/ff 接口，0x8000~~0xFFFF 用于 event 接口。同一服务内 IfID 唯一。

StrmID 用途：请求-响应匹配、多路复用（同一对端并发多请求）、CON 去重（见 §5.5）、订阅会话标识（Subscribe 生命周期，见 §7.2）、GetIDL 查询关联（见 §7.2）。数据帧不携带**服务版本**（MajorVer/MinorVer）；协议版本见帧头 VER。

**控制帧 StrmID 语义**：控制帧去重键为 `(peer, 0x0000, 0x00, StrmID)`——StrmID=0x00 为连接级帧（REN/心跳/Offer/Find）；StrmID=0x01\~0x7F 为请求-响应型控制交互：Subscribe 携带客户端分配的会话 StrmID（同一订阅会话的首次订阅、保活、取消全程复用同一 StrmID），GetIDL 携带客户端分配的查询 StrmID（响应/RST 回显，支持同一 TCP 连接上并发查询，见 §7.2）。同一时刻同一对端上，控制帧键 `(peer,0,0,StrmID)` 内的活跃 StrmID 必须唯一（Subscribe 会话与 GetIDL 查询共用该键空间）；控制帧键与数据帧键因 SvcID=0 仅控制帧而天然不相交，编号空间可复用，无需隔离。

**服务实例唯一性规则**：

| 层级                      | 唯一性范围        | 说明                |
| ----------------------- | ------------ | ----------------- |
| `SvcID`                 | 全局唯一         | 服务标识，各节点共享同一份 IDL |
| `(SvcID, InstID)`       | 全局唯一（跨节点）    | 唯一标识一个服务实例        |
| `(SvcID, IfID, InstID)` | 全局唯一（由上一行推导） | 唯一标识一个接口端点        |

- 同一节点内，同一 `SvcID` 可以注册多个 `InstID`（多实例部署）

- `(SvcID, InstID)` 跨节点唯一是**运行前提**，由部署规划保证；违反时行为未定义

- 客户端可用 `(SvcID, InstID)` 直接定位服务实例，不依赖源地址

- 同一 `(SvcID, InstID)` 的所有接口必然来自同一源地址

### 3.6 REN 重启标志

REN=1 时 CTR 必须为 1，数据帧 REN 恒为 0。REN=1 的帧固定：TYP=NON，StrmID=0x00，Code=0x00。

**发送规则**：

- REN 经 **UDP 组播**发送（覆盖 UDP 侧缓存清理），固定 TYP=NON（不用 CON，无重传状态机）

- 为规避丢帧，**连续发送 3 次**，相邻两份之间间隔 \~100ms——交换机缓冲溢出导致的丢包是突发的，隔开发送才能将全丢概率压至独立丢包率的三次方；背靠背连发会一起丢

- 接收端清缓存天然幂等，无需去重

- graceful shutdown 时序：**先组播 REN ×3，再释放资源 / 关闭 TCP 连接**

- **双角色节点均发 REN**：纯订阅方（客户端）重启时同样发 REN——订阅表靠 TTL 自愈，但显式 REN 可加速服务端清理订阅者

- TCP 侧不依赖 REN：连接断开事件触发同等清理（见 §5.6），REN 主要覆盖 UDP 侧

收到 REN=1：清除该节点的所有服务缓存，清空该对端的全部活跃 Stream 与待确认重传记录，重置 StrmID 分配游标，等待 SD Offer 重建。REN 仅影响该对端节点。

StrmID 不在该对端活跃表中时，ACK/RST 直接丢弃。

**迟到帧统一规则**：StrmID 不在该对端活跃表中时，**数据帧静默丢弃**，ACK/RST 丢弃；控制帧 0x11（GetIDL 响应）与 RST 同样静默丢弃（非活跃查询 StrmID 的迟到响应，配合 §6.1 释放/冷却防误配）。重复 Response（去重后迟到）、迟到 Notification 等均适用本条。

### 3.7 TYP 传输语义

| TYP | 名称  | 语义              | 允许的 Code                      | 适用场景                                                  |
| --- | --- | --------------- | ----------------------------- | ----------------------------------------------------- |
| 00  | NON | 不确认，尽力投递        | 任意                            | TCP 上所有帧；UDP 上的周期事件、日志、SD                             |
| 01  | CON | 需 ACK 确认（仅 UDP） | 任意                            | UDP 上的 Request、Fire-Forget、可靠事件、Subscribe 首次/取消       |
| 10  | ACK | 传输层确认（仅 UDP）    | 数据帧场景仅 0x00；控制帧场景 0x00 或 0x10 | 空确认（Code=0x00，不承载应用数据）；Subscribe 确认（Code=0x10，见 §8.1） |
| 11  | RST | 拒绝/重置           | 错误码                           | 未知服务、拒绝连接；Code 指明原因                                   |

**规则**：

- 收到 CON 帧（UDP）后，回一个空确认 ACK（Code=0x00）；Subscribe(TTL>0) 的确认例外——回 `TYP=ACK, Code=0x10`（订阅建立确认，兼作传输确认，有/无缓存一致，见 §8.1）；Subscribe(TTL=0) 取消按一般 CON 回空确认 ACK(Code=0x00，回显会话 StrmID)

- 收到 NON 帧，不回任何确认

- TCP 上不使用 CON/ACK，所有帧为 NON——TCP 自带可靠有序传输，CON/ACK 冗余且逐帧增加 RTT，无收益；TCP 上收到 TYP∈{CON, ACK} → 协议违规，回 RST(0x00)

- **ACK/RST 帧的 PLB 必须为 0**（无 Payload）；PLB>0 → 视为协议违规，回 RST(0x00)（见 §4.3 步骤 2）

### 3.8 大数据传输约束

协议层**不提供分段/重组机制**。大数据由服务契约在 IDL 阶段约束：

| 场景           | 策略                                                                                                                           |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| 常规 UDP 接口    | IDL 声明字段 `max_len` 与接口级 `max_payload`（≤ `max_payload_len`=1400），编解码层强制校验，超限拒绝                                                |
| 大数据接口（> MTU） | IDL 声明 `transport: "TCP"`；TCP 为流式传输，单帧可承载完整 IDL 对象（如 1MB Blob），不受 `max_payload_len` 约束，仅受接口级 `max_payload` 与字段级 `max_len` 约束 |
| 应用层分块（可选）    | 若需在 UDP 上分块，由应用语义自行定义块序号与重组（协议栈不感知），并应保证块级幂等或可重传                                                                             |

超限帧的处理：编码侧报错；接收侧丢弃并回 RST(0x23)（仅 UDP；TCP 侧超限为接口级 `max_payload`/字段级 `max_len` 校验失败，按 0x20 Bad Request 处理）。协议栈不做运行时自动降级或拆分。

## 4. 帧解析

### 4.1 TCP 流式解析

- 帧边界由 Payload Length 确定，无额外帧分隔符

- 解析状态：`IDLE → READ_CTRL_SVC(4B) → READ_IF_INST_STRM(4B) → READ_LENGTH(plb,条件) → READ_MASK(4B,条件) → READ_PAYLOAD(length) → FRAME_COMPLETE → IDLE`
  （`READ_CTRL_SVC` = 2B 控制头 byte0/byte1 + SvcID 高 2B；`READ_IF_INST_STRM` = SvcID 低 2B + IfID 2B + InstID 1B + StrmID 1B，与 §3.1 帧头布局对齐）

- **分包**：任何阶段（含 Length 字段本身、Masking Key、Payload Data）数据不足时，保存当前解析状态并等待后续数据，不得丢弃已读字节

- **粘包**：一次接收含多帧时，逐帧解析并在每帧完整后立即交付

- **半帧超时（两阶段机制）**：一个帧开始接收后超过 `tcp_frame_timeout_ms`（默认 5000ms）仍未收完，按帧头是否完整分两阶段处理：

  | 阶段                 | 触发条件                                     | 处理                                                                                      |
  | ------------------ | ---------------------------------------- | --------------------------------------------------------------------------------------- |
  | 一：帧头不完整（已收 < 8B）   | 帧总长不可知，无法确定丢弃边界                          | 回 RST(0x26) 并**关闭连接**——后续字节无法重同步；客户端按 §5.6 自动重连                                         |
  | 二：帧头完整、Payload 不完整 | 帧头已收齐（≥8B，含 Length/Masking Key），帧总长 L 已知 | 回 RST(0x26)，进入**丢弃模式**：按帧头声明精确丢弃该帧剩余 R = L − 已收字节 → 收满 R 后恢复 `IDLE` 正常接收，**连接不关闭、继续复用** |

  **RST(0x26) 语义**："当前帧作废，请机械发完剩余字节"。发送端收到后应将本次请求/推送**标记为失败**（不等响应、不再重传），但仍需把当前帧剩余字节发完——TCP 字节流无法取消已排队数据，撤销发送会破坏流边界；内容已无关紧要，接收端将按丢弃边界精确忽略。RST(0x26) 为与正向流方向相反的独立反向帧，不占用/污染发送端的正向字节流。

  **丢弃模式退出条件（三者之一）**：

  1. 收满剩余 R 字节 → 恢复正常接收（`IDLE`），连接继续复用
  2. 对端 EOF/RST 断开 → 随连接关闭一并处理（进程死亡时操作系统必然关闭连接，接收端立即感知，无需依赖超时）
  3. 兜底超时 → 关闭连接。兜底时长 = `2 × tcp_frame_timeout_ms`（协议固定倍率，不新增配置项）；丢弃模式中每收到任意字节即刷新计时（对端仍在发送则不触发，容忍持续慢速传输）

- **频繁半帧（实现建议，非协议要求）**：实现可统计半帧频次，连续 N 次（建议 N=3）半帧可主动断连并告警——通常指示对端实现缺陷或网络质量恶化。协议不定义该行为，不影响一致性判定

### 4.2 UDP 报文解析

- 每个 UDP 数据报承载一帧，无粘包问题

- 数据报长度 < 最小帧长度（8B）→ 丢弃

- 数据报长度 ≠ 帧头声明长度（多余或不足）→ 一律视为错误并丢弃（不做截断）

- Payload 超过 `max_payload_len` → 丢弃并回 RST(0x23)（`max_payload_len` 仅 UDP 适用，见 §2）；IDL 级上限（max\_payload/max\_len/fixed\_len）在解码阶段校验，失败按 0x20 处理（见 §9.3/§12.1，TCP/UDP 一致）

### 4.3 解析流程

```
1. 读 byte0 → CTR/REN/VER/MSK/PLB
   校验 VER 与本端相等
     不等 → 单播帧回 RST(0x22)、组播帧静默丢弃
   校验 CTR/REN 一致性：REN=1 时 CTR 必须为 1
     失败 → 回 RST(0x00) 并丢弃
   校验 CTR=1 时 MSK=0（控制帧固定无掩码、不附加 CRC，见 §9.6/§10）
     失败 → 回 RST(0x00) 并丢弃
2. 读 byte1 → TYP/Code
   校验 REN=1 时 TYP=NON 且 Code=0x00
   校验 TYP=ACK 时 Code∈{0x00, 0x10(仅 CTR=1)} 且 PLB=0
   校验 TYP=RST 时 PLB=0 且 Code∈{0x00} ∪ 0x20~0x3F
   校验 TCP 传输上 TYP∉{CON, ACK}（TCP 不使用 CON/ACK，见 §3.7）
   校验 UDP 传输上 CTR=1 且 Code=0x04（GetIDL 仅 TCP 单播，见 §7.2）
   校验失败 → 回 RST(0x00) 并丢弃
3. 读 SvcID/IfID
   校验控制帧 SvcID=0x0000 且 IfID=0x0000
   校验数据帧 SvcID≠0x0000 且 IfID≠0x0000（ID=0 通配仅 SD Entry 场景，见 §3.5）
4. 读 InstID/StrmID
   校验控制帧 InstID=0、REN=1 时 StrmID=0、数据帧 InstID≠0x00
   校验控制帧 StrmID：0x00（连接级）或 0x01~0x7F（Subscribe 会话 / GetIDL 查询，见 §7.2）
   校验控制帧 StrmID 语义：Code∈{0x03,0x04} 时 StrmID∈0x01~0x7F；Code∈{0x00,0x01,0x02} 时 StrmID=0x00
     违反 → 回 RST(0x00) 并丢弃（组播帧静默丢弃）
   校验数据帧 StrmID∈0x01~0xFE（0x00=连接级、数据帧禁用；0xFF 保留；越界 → RST(0x00)）
5. 若 PLB>0 读 Payload Length(plb 字节)；PLB=0 时 Length=0
   UDP：超 max_payload_len → 回 RST(0x23)（TCP 无此校验，见 §2）
6. 若 MSK=1 读 4B Masking Key
7. 读 Payload Data；MSK=1 则 XOR 还原
8. 组装 Frame 交付
```

### 4.4 解析错误处理

| 错误场景                                                              | 处理方式                                                            |
| ----------------------------------------------------------------- | --------------------------------------------------------------- |
| VER 与本端不一致                                                        | 单播帧回 RST(0x22)，组播帧静默丢弃                                          |
| CTR/REN 不一致 / SvcID/IfID 越界 / ACK·RST 带载荷                         | 回 RST(0x00)，丢弃帧（组播帧静默丢弃）                                        |
| TCP 数据不足（半帧/分包）                                                   | 保存状态，等待更多数据                                                     |
| UDP 数据报长度 ≠ 声明帧长度                                                 | 丢弃数据报（不截断）                                                      |
| Payload 超过 max\_payload\_len（仅 UDP，帧级校验）                          | 回 RST(0x23)，丢弃帧                                                 |
| IDL 级字节契约校验失败（字段越界/截断、`fixed_len` 不符、`max_len` 超限、`bool` 非法、`enum` 超出 `base` 值域、CRC 失败等，解码阶段） | 回 RST(0x20)，丢弃帧（TCP/UDP 一致，见 §12.1）                             |
| TCP 半帧超时——帧头不完整（<8B）                                              | 回 RST(0x26)，丢弃残缺帧，**关闭连接**（帧总长不可知，无法重同步；客户端按 §5.6 自动重连）         |
| TCP 半帧超时——帧头完整、Payload 不完整                                        | 回 RST(0x26)，进入丢弃模式按帧头声明的帧总长精确丢弃剩余字节，收满后恢复正常接收，**连接不关闭**（见 §4.1） |
| UDP 上收到 GetIDL（CTR=1, Code=0x04）                                  | 回 RST(0x00)，丢弃帧（GetIDL 仅 TCP 单播，传输绑定违规，见 §7.2；组播帧静默丢弃）          |

## 5. 交互语义与时序

### 5.1 Request-Response

```
客户端 --- Request(StrmID=0x01) ---> 服务端
客户端 <--- Response(StrmID=0x01) --- 服务端
```

| 传输  | Request TYP | Response TYP    |
| --- | ----------- | --------------- |
| TCP | NON         | NON             |
| UDP | CON         | CON（对端回空确认 ACK） |

**Response 必须回显请求的 StrmID**；服务端流（0x80\~0xFE）仅用于服务端主动发起的 Notification。

**Response 帧形态**：`CTR=0, TYP=NON/CON（按请求的传输）, Code=0x10（OK）`。错误一律以 RST(Code) 表达（0x2x 客户端错误 / 0x3x 服务端错误，见 §12.1），不用数据帧承载错误。

**Response 不使用 TYP=ACK**：响应是应用数据，ACK 是纯传输层确认。

客户端启动应用层响应超时定时器（默认 2000ms，可逐次覆盖），收到 Response 即取消，**并一并取消该 StrmID 的待确认重传**（见 §5.5）。

### 5.2 Fire-Forget

```
客户端 --- Fire-Forget ---> 服务端
```

| 传输  | TYP             |
| --- | --------------- |
| TCP | NON             |
| UDP | CON（对端回空确认 ACK） |

FF 无应用层响应，无应用层超时；送达保证由传输层 CON/ACK 承担（仅 UDP）。

### 5.3 事件推送（Notification）

```
服务端 --- Notification(TYP=NON) ---> 客户端A  (UDP, 尽力投递)
服务端 --- Notification(TYP=CON) ---> 客户端B  (UDP, 需送达保证)
```

- TCP：`TYP=NON`

- UDP 常规事件：`TYP=NON`，无 ACK

- UDP 可靠事件：`TYP=CON`，客户端回空确认 ACK，超时重传（见 §5.5）

多客户端推送同一事件，每个客户端独立分配 StrmID。CON 模式需每个客户端独立 ACK，去重键 = `(peer, svc_id, inst_id, StrmID)`。

### 5.4 RST 触发场景矩阵

| 场景       | 触发方 | RST 内容             | 接收方动作                              |
| -------- | --- | ------------------ | ---------------------------------- |
| 未知服务/接口  | 服务端 | TYP=RST, Code=0x24 | 记录错误，释放 Stream                     |
| 不支持的操作码  | 服务端 | TYP=RST, Code=0x25 | 记录错误，释放 Stream                     |
| 请求格式错误   | 服务端 | TYP=RST, Code=0x20 | 记录错误，释放 Stream                     |
| 版本不支持    | 接收方 | TYP=RST, Code=0x22 | 报错，不可通信                            |
| 协议违规     | 接收方 | TYP=RST, Code=0x00 | 记录错误                               |
| TCP 半帧超时 | 接收方 | TYP=RST, Code=0x26 | 标记本次传输失败，机械发完当前帧剩余字节（见 §4.1 两阶段机制） |

> RST **回显触发帧的 StrmID**，接收方据此匹配释放对应 Stream/订阅会话（会话 StrmID 场景见 §7.2）。

### 5.5 CON/ACK 可靠性（仅 UDP）

| 传输协议 | 可靠性来源              | 丢失处理                    |
| ---- | ------------------ | ----------------------- |
| TCP  | TCP 协议自身           | 无需处理                    |
| UDP  | CON + ACK + 指数退避重传 | 最多 4 次发送（1 次原始 + 3 次重传） |

**重传参数**：

| 参数            | 默认值                               |
| ------------- | --------------------------------- |
| `interval_ms` | 200ms                             |
| `max_retry`   | 3（不含首次）                           |
| 退避公式          | `interval * 2^retry`              |
| 末次发送后等待       | `interval * 2^max_retry` = 1600ms |

**发送与重传时间线**：

| 事件       | 时刻               |
| -------- | ---------------- |
| 首次发送     | 0ms（同时启动应用层响应超时） |
| 重传 1     | 200ms            |
| 重传 2     | 600ms            |
| 重传 3（末次） | 1400ms           |
| 停止重传     | 3000ms（静默停止，不报错） |

**重传耗尽语义**：

- 重传耗尽仅表示停止重发，不代表响应不会到达

- 请求成败由应用层响应超时统一判定，传输层不产生独立错误

- 响应超时触发时，若该 StrmID 仍有待确认重传，一并取消

- 若响应超时大于停止重传时刻（3000ms），3000ms 后进入"不再重传但仍等待响应"状态，超时前收到响应仍算成功

**重传范围**：UDP 上所有 TYP=CON 的帧（数据帧 Request、Notification CON；控制帧 Subscribe 首次/TTL=0）均走重传。NON 帧与 SD 周期帧不需要。非 Request 的 CON 无应用层响应超时，由 TTL 与保活机制兜底。

**去重语义（幂等保障）**：StrmID 是重传去重键，去重需收发双方配合：

| 角色  | 规则                                                                                                                                                                                         |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 发送方 | 同一 `(peer, svc_id, inst_id, StrmID)` 的待确认帧只允许一个；重传使用同一 StrmID 和完全相同的字节。控制帧键为 `(peer, 0, 0, StrmID)`——Subscribe 会话 StrmID（§3.5）使不同订阅会话可并发，"同键唯一"对每个会话独立成立                                   |
| 服务端 | 收到与当前活跃 StrmID 相同的请求（即重传）时，直接重发上次缓存的响应，不重新执行处理逻辑。**对控制帧 Subscribe 同样适用**：同一会话 StrmID 的重复 CON Subscribe → 重发该会话确认——TTL>0 重发 `ACK(Code=0x10)`、TTL=0 重发 `ACK(Code=0x00)`——不重新执行、不重推全量（见 §8.1） |
| 服务端 | 响应缓存按 `(peer, svc_id, inst_id, StrmID)` 保存，随 Stream 释放（收到 ACK / 超时 / RST）一并清除。控制帧的确认缓存同理按会话 StrmID 保存与清除                                                                                   |
| 客户端 | 重复收到同一响应时，按 StrmID 判定为重复并丢弃，只交付首个                                                                                                                                                          |

**服务端重启窗口的幂等语义**：服务端重启后响应缓存丢失，此时收到的重传请求将**重新执行处理逻辑**——传输层幂等在重启窗口失效，应用层幂等由服务契约保证（如 IDempotent 标注的接口语义）。客户端侧因 REN ×3 已清空重传记录，此窗口仅在 REN 三发全部丢失时出现（概率 \~p³）。

### 5.6 TCP 连接策略

- 连接建立：客户端主动发起 TCP 连接到服务端 (IP, Port)，按 (IP, Port) 建立唯一长连接

- 多路复用：同一 TCP 连接承载所有 SvcID/IfID 的数据帧，StrmID 实现多路复用

- 服务端：启动时 bind + listen，accept 新连接后纳入帧解析

- 连接断开：清理该连接的所有 Stream 和订阅关系，通知应用层

- 自动重连：客户端检测到连接断开后重连；重连成功后重新触发 SD 流程

- **双角色节点互连**：A、B 同时为服务端与客户端时，各按客户端角色**独立发起并维护自己的出站连接**（两条单向连接并存），不尝试复用对方连接——每条连接的 Stream/StrmID 分配、心跳、重连策略各自独立，互不干扰

### 5.7 心跳（Ping，仅 TCP）

**目的**：检测 TCP 半开连接、保持 NAT 映射。

**Ping 帧**：CTR=1, REN=0, TYP=NON, Code=0x00, SvcID=0x0000, IfID=0x0000, InstID=0x00, StrmID=0x00, Payload 空

**规则**：

| 规则        | 说明                                                        |
| --------- | --------------------------------------------------------- |
| 空闲时发 Ping | 见下方"空闲"定义；收到 Ping 不回任何帧                                   |
| 存活计时      | 收到任意帧（数据帧或控制帧）即刷新；超过 `2 × heartbeat_period` 未收到任何帧，标记连接失效 |
| 对称策略      | 双角色节点执行同一策略：各自按空闲条件主动发 Ping，各自靠接收判定对端存活，无需回应              |

**"空闲"定义**：自本端上次发出任意帧（数据帧或控制帧）起，超过 `heartbeat_period`（默认 30s）未发送任何帧，则发送一次 Ping。

**UDP 场景**：不需要心跳（无连接状态），SD Offer/Subscribe 的周期报文已提供等价的可达性探测。

## 6. Stream

### 6.1 StrmID 空间

| 范围         | 语义    | 分配方 | 用途                                                                |
| ---------- | ----- | --- | ----------------------------------------------------------------- |
| 0x00       | 连接级控制 | 双方  | 数据帧无；控制帧 REN、心跳 Ping、Offer、Find                                   |
| 0x01\~0x7F | 客户端流  | 客户端 | 数据帧：客户端发起的 Request、Fire-Forget；控制帧：Subscribe 会话、GetIDL 查询（见 §7.2） |
| 0x80\~0xFE | 服务端流  | 服务端 | 服务端主动推送的 Notification                                             |
| 0xFF       | 保留    | —   | 未来扩展                                                              |

客户端流编号空间（0x01\~0x7F）在数据帧与控制帧（Subscribe 会话、GetIDL 查询）间复用——控制帧键 `(peer,0,0,StrmID)` 与数据帧键 `(peer,svc≥1,inst,StrmID)` 因 SvcID 区分而天然不相交（见 §3.5）。Response 不占用服务端流：Response 必须回显请求的 StrmID（见 §5.1），属于客户端流编号空间。

订阅会话 StrmID 的分配/释放独立于数据帧 Stream 生命周期管理（不进入 §6.2 状态机）；同一会话在首次订阅 → 保活 → 取消全程复用同一 StrmID，取消确认（传输 ACK Code=0x00，见 §8.1）到达后释放/冷却；实例转 Expired 时旧会话 StrmID 一并释放/冷却。GetIDL 查询 StrmID 同理：协议栈为每次查询分配临时 StrmID（独立于 Stream 状态机），收到响应/RST 或查询超时后释放/冷却（**冷却语义与订阅会话一致，见 §6.3**——防释放后立即复用时旧查询的迟到 0x11 响应误配新查询）。

### 6.2 Stream 生命周期

```
       +----------------+
  +--->|    Closed      |
  |    | (初始/释放后)  |
  |    +--------+-------+
  |             |    alloc_client_stream / alloc_server_stream
  |             v
  |    +--------+-------+
  +----|    Active      |
       | (可收发数据)   |
       +----------------+
```

| 当前状态   | 事件                          | 下一状态   |
| ------ | --------------------------- | ------ |
| Closed | 分配 StrmID                   | Active |
| Active | 收到/发送 RST                   | Closed |
| Active | 本地主动关闭                      | Closed |
| Active | Request 收到 Response         | Closed |
| Active | Notification 发送完成（NON）      | Closed |
| Active | Notification 确认收到或重传耗尽（CON） | Closed |
| Active | Fire-Forget 发送完成（NON）       | Closed |
| Active | Fire-Forget 确认收到或重传耗尽（CON）  | Closed |

**CON 模式的关闭时机**：CON Notification / CON Fire-Forget 的 Stream **保持 Active 至 ACK 收到或重传耗尽**——Stream 过早关闭会导致 StrmID 被复用，新旧帧的 ACK 匹配错乱。NON 模式发送完成即关。

### 6.3 StrmID 管理规则

- StrmID 按 `(peer, svc_id, inst_id)` 隔离；每个组合内 client(0x01~~0x7F) 与 server(0x80~~0xFE) 各 127 个，独立循环分配

- `peer` 用于连接级隔离：同一 peer 内同一 `(svc_id, inst_id)` 只对应一个实例（见 §3.5）

- 目标 StrmID 仍活跃时跳过，寻找下一个空闲

- 收到 REN=1 时清除该对端全部序列

- 分配应优先选用已冷却的 StrmID；**冷却定义**：该 StrmID 距上次释放后，本组合内已完整轮转分配过一轮（或 ≥ 2 次其它 StrmID 分配）——避免旧帧迟到时与新会话冲突

- 控制帧 StrmID（订阅会话 + GetIDL 查询）按 `(peer)` **统一分配池**隔离（同键内活跃 StrmID 必须唯一，见 §3.5/§6.1），与数据帧管理规则独立

## 7. 服务发现（SD）

控制帧（CTR=1）承载服务发现协议，帧格式与数据帧完全相同：Offer/Find/Subscribe 走 UDP（组播或单播），GetIDL 走 TCP 单播（见 §7.2）。

统一规则：

- 帧头 SvcID/IfID 固定为 0x0000/0x0000，所有服务信息在 Payload Entry 中

- 周期性 SD 帧（Offer/Find/Subscribe）仅承载**实例在线信息**（是否在线、在哪个源地址）；接口集合由 IDL 定义（纯动态运行时加载，见 §11.1）。**客户端本地 IDL 库缺失时经 GetIDL 自动拉取**（§7.2，唯一走 TCP 单播的 SD 操作）

### 7.1 SD Entry 格式

```
  Offer Entry (6B):       Find Entry (4B):      Subscribe Entry (7B):    GetIDL Entry (3B):
    uint16  SvcID           uint16  SvcID         uint16  SvcID            uint16  SvcID
    uint8   InstID          uint8   InstID        uint16  IfID             uint8   MajorVer
    uint8   MajorVer        uint8   MajorVer      uint8   InstID
    uint8   MinorVer                              uint8   GrpId
    uint8   TTL(0=停止)                           uint8   TTL(0=取消,秒)
```

- **Offer / Find Entry 不含 IfID**：服务在线与否是实例级 `(SvcID, InstID)` 事实，与提供哪些接口无关

- **Find Entry 不含 MinorVer**：MinorVer 不参与匹配（见 §11.2），携带无语义

- **Subscribe Entry 保留 IfID**：订阅是接口级行为（订阅某个具体 event 接口或事件组），需指明 IfID 或 GrpId

- **GetIDL Entry 无 InstID**：IDL 是**服务级事实**（各节点共享同一份 IDL，见 §3.5），同一 SvcID 的所有实例内容相同，InstID 不参与定位（服务端按 SvcID+MajorVer 匹配任一在线实例读其 IDL）；MajorVer 为查询的版本匹配参数

**GrpId 语义**：服务内 8bit 组号（0x00=不使用组，按 IfID 单接口订阅；0x01\~0xFF=组号）。用 GrpId 订阅时 IfID 必须为 0x0000，服务端展开为组内所有 event 接口。组定义在 IDL `event_groups` 中声明（见 §11.1）。

**Subscribe Entry 合法组合**（Offer/Find Entry 无 IfID 字段，Subscribe Entry 有——订阅是接口级行为）：

- 单接口订阅：`IfID≠0x0000 且 GrpId=0`

- 组订阅：`IfID=0x0000 且 GrpId≠0`（服务端展开为组内所有 event 接口）

- `IfID=0x0000 且 GrpId=0` 为**非法组合**（既非单接口也非组）：该 Entry 丢弃并记 Error 日志（见 §7.2 Entry 级处理）

### 7.2 SD 操作语义

| 操作        | Code | Payload                               | 传输                                                                                   | 语义                                                                                                                                                                                             |
| --------- | ---- | ------------------------------------- | ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Offer     | 0x01 | N × Offer Entry                       | UDP 组播，周期 `period`                                                                   | TTL=0 表示停止提供；不携带 Endpoint（IP 由 socket 源地址获取）                                                                                                                                                   |
| Find      | 0x02 | 空 或 N × Find Entry                    | UDP 组播                                                                               | 空 Payload = 查询所有服务；带 Entry 时必须指定 SvcID（非零），InstID 可 0x00 通配SvcID 非通配时 MajorVer 参与精确匹配，MinorVer 不参与匹配响应帧格式与 Offer 相同（Code=0x01），由服务端 UDP 单播发送；**响应超限时适用下方同一拆帧策略**                               |
| Subscribe | 0x03 | N × Subscribe Entry                   | UDP 单播，首次 CON / 取消（TTL=0）CON / 保活 NON，周期 `period`；**帧携带会话 StrmID（0x01\~0x7F，客户端分配）** | Entry 携带 TTL(秒)，TTL=0 表示取消订阅（延迟到下次 tick 移除）；同一订阅会话（首次/保活/取消）全程复用同一 StrmID；首次 CON 的服务端回应见 §8.1；**同会话 StrmID 的重复 CON 到达 = 重传判定**（服务端重发上次确认，见 §5.5/§8.1）；NON 保活到达 = TTL 刷新；TTL 倒计时归零视为离线          |
| GetIDL    | 0x04 | 1 × GetIDL Entry（3B：SvcID + MajorVer） | **仅 TCP 单播**；帧携带查询 StrmID（0x01\~0x7F，客户端分配）                                          | 查询服务 IDL 全文；服务端回 Code=0x11（**回显请求 StrmID**，Payload=完整 IDL JSON 文本）；本地库无该 (SvcID, MajorVer) 已加载定义 / MajorVer 不匹配 → RST(0x24)；Payload ≠3B → RST(0x20)；UDP 上收到 → RST(0x00)（传输绑定违规）；详见下方 GetIDL 语义 |

**Subscribe 会话 StrmID 规则**：

- 客户端为每个订阅会话（一次 `subscribe()` 调用）分配 0x01\~0x7F 中一个 StrmID，同一订阅的首次 Subscribe(TTL>0, CON) → 保活 Subscribe(TTL>0, NON) → 取消 Subscribe(TTL=0, CON) 全程复用；会话结束（取消完成）后释放/冷却

- 服务端按 `(peer, StrmID)` 判定"重传 vs 新操作"；订阅表主键仍为 Entry 内容 `(peer, svc_id, if_id/grp_id, inst_id)`，StrmID 仅作会话跟踪——客户端重启后换新 StrmID 重订同一服务，按 Entry 级刷新，状态自洽

- 一个 Subscribe 帧可携带 N×Entry（合并订阅/取消），同一会话 StrmID 下 Entry 级独立处理

**GetIDL 语义（Code=0x04 → 0x11，仅 TCP 单播）**：

- **定位**：GetIDL 是**协议栈内部行为**，应用层无感知（不提供应用层查询 API）——纯动态架构下（§11.1）协议栈运行时按需获取服务定义，是"热插拔服务"闭环的核心机制（客户端按需拉取 + 服务端注册时集群同步，双角色统一）

- **请求帧形态**：`CTR=1, TYP=NON, Code=0x04, SvcID=IfID=InstID=0x0000/0x00, StrmID=协议栈分配 0x01~0x7F`，Payload = 1 × GetIDL Entry（3B：SvcID 必填非 0 + MajorVer 精确匹配）

- **触发条件（协议栈自动，双角色统一机制）**：应用请求需要编解码某服务（**调用/订阅/接收事件**——客户端角色）或**注册服务实例**（`register_service`，服务端角色）且**本地 IDL 库中不存在该 (SvcID, MajorVer)** 时：

  1. 查 SD 发现缓存：存在该服务在线实例 → 向其发起 GetIDL（TCP，复用 §5.6 连接策略，与 rpc/tcp-event 共用同一条长连接）→ 落盘加载后继续原操作
  2. 发现缓存无在线实例 → 不发起查询，当前操作直接失败（服务不可用，错误上抛应用）

  - 服务端注册场景：拉取的 MajorVer 取自发现缓存（集群当前在线版本），落盘加载后注册继续——**新节点部署只需业务代码（handler），IDL 定义自动从集群同步，无需人工分发**

- **服务端处理**：按 `(SvcID, MajorVer)` 在本地 IDL 库定位**任一**匹配的**已加载 IDL 定义（与实例是否在线无关）**——IDL 为服务级事实，InstID 不参与（见 §7.1）；实例注销不卸载定义（定义生命周期 = IDL 库文件，独立于实例 handler）。定位后读取其 IDL JSON 全文回响应——纯协议栈行为，应用无感知

- **响应帧形态**：`CTR=1, TYP=NON, Code=0x11, StrmID=回显请求值`，Payload = 完整 IDL JSON 文本（UTF-8，无长度前缀——Payload Length 即长度，无 Entry 前缀——IDL 自含 svc\_id/版本，协议栈落盘前须校验与请求一致，不一致按查询失败处理）

- **落盘与加载（协议要求）**：拉取成功后，协议栈**将 IDL 持久化写入本地 IDL 库**（文件形式，见 §11.1）→ 解析加载 → 继续当前请求的编解码。持久化保证协议栈重启后本地命中，无需重复拉取；**落盘失败**（磁盘满/只读等）时**降级为仅内存加载使用**并记 Error 日志（可用性优先，重启后需重新拉取）

- **仅 TCP 的原因**：IDL JSON 文本可达数 KB\~数十 KB，UDP `max_payload_len`（1400）不可行，且 JSON 拆帧重组复杂；TCP 单帧承载完整对象（§3.8 既有原则）。UDP 单播收到 GetIDL → RST(0x00)（传输绑定违规，类比 TCP 收 CON/ACK）；组播帧按 §4.3 既有规则静默丢弃

- **并发查询关联**：TCP 流式无报文边界，同一连接可并发多个 GetIDL（不同 StrmID），响应/RST **回显请求 StrmID**，协议栈据此匹配（与 rpc Response 回显模式一致，见 §5.1）；控制帧键 `(peer,0,0,StrmID)` 与数据帧键天然不相交（§3.5），GetIDL 与 Subscribe 会话共用控制帧键空间，同一时刻同键内活跃 StrmID 必须唯一

- **错误场景**：本地 IDL 库中**无该** **`(SvcID, MajorVer)`** **已加载定义**（含服务从未部署、定义已卸载、MajorVer 不匹配）→ RST(0x24，回显 StrmID)；Payload **≠ 3B**（残缺 <3B 或多余 >3B，非 1×Entry）或 SvcID=0 → RST(0x20，回显 StrmID)；查询失败（0x24/0x20/超时/连接断开）→ 当前请求失败，错误报应用，IDL 库状态不变（不写入失败结果）

- **幂等与重发**：纯查询、服务端无状态，请求幂等；TCP 自身保障可靠传输，无传输层重传；**查询超时复用** **`response_timeout_ms`**（GetIDL 为请求-响应交互，见附录 A），超时后协议栈可重发（换新 StrmID，重发次数由实现定）；拉取失败 → 当前操作（调用/订阅/注册）失败上抛，由应用决定重试

- **版本演进**：IDL 库按 `(SvcID, MajorVer)` 组织；服务端升级 MajorVer 后，客户端经 Offer/发现缓存获知新版本 → 本地无该版本 → 自动重新拉取（新旧版本定义并存，不覆盖）；同一 SvcID 跨 MajorVer 并存属部署异常，注册拉取时实现取任一版本（建议最高版本）

- **实现建议（非协议要求，不进一致性判定）**：同一 `(SvcID, MajorVer)` 的并发首次请求可合并为单次查询（其余等待结果）；IDL 库可监听文件变化实现服务端热加载（见 §11.1）

**Entry 级处理与失败反馈**：帧内 Entry 逐条独立处理；无效 Entry（格式错误、组合非法\[见 §7.1]、服务/实例不存在）**丢弃并记 Error 日志**，不影响同帧其他 Entry。服务端能正常解析帧（帧头 + Entry 列表完整）即按会话回确认（TTL>0 → `ACK(Code=0x10)`；TTL=0 → `ACK(Code=0x00)`）——**Entry 级成败不逐项反馈**，客户端通过事件到达情况与 `find_service`/`is_available` 感知（见 §13.2）。整帧 Payload 无法解析 → RST(0x20)。

**tcp-event 推送通道**：event 接口声明 `transport: "tcp"` 时，客户端应**先建立 TCP 连接再订阅**；服务端收到该类 Subscribe 时无来自该客户端的活跃 TCP 连接 → 回 RST(0x24)。推送复用该连接（TYP=NON，见 §5.3，按订阅者源 IP 匹配活跃连接）；连接断开期间推送暂停（**不缓存补发**），**订阅记录保留**（按订阅 TTL 正常维护，不随连接断开失效），客户端重连后推送自动恢复（见 §12.3）

**SD Offer/Find 帧大小约束**：编码后总字节数（含帧头 + SD 头 + N×Entry）应 ≤ `max_payload_len`。

**SD Offer 拆帧策略**（**仅 UDP**——TCP 由 TLV Length 自然承载完整帧，无拆帧概念）：

- 拆帧阈值 = `min(UDP MTU 有效载荷（典型以太网 ≈1472B）, max_payload_len=1400)` = 1400

- 若 Entry 总数导致 Payload 超过阈值，按阈值最大满装拆分为多个 Offer 帧，同周期内连续发送

- 每个 Offer 帧自包含、逐帧独立处理：客户端收到任一帧即按其中的 Entry 更新注册表

- Entry 粒度 = `(SvcID, InstID)`，即一个实例一条 Entry

- 部分 Offer 帧丢失由 TTL 机制兜底（下一周期重新广播）

**实例冲突处理**：客户端按 `(SvcID, InstID)` 记录实例与源地址：

| 场景               | 客户端行为                                                              |
| ---------------- | ------------------------------------------------------------------ |
| 源地址 == 该实例已记录源地址 | 正常刷新 TTL                                                           |
| 源地址 ≠ 已记录源地址     | 记录 Error 级日志（含 `(svc_id, inst_id)` 与两个源地址），保留先到的实例记录不变，忽略后到的 Entry |

冲突属部署配置错误，协议层不做仲裁或自动切换。

### 7.3 服务端视角 — 服务生命周期

```
      +----------------+
      |   NotOffered   |
      | (未注册到本地) |
      +--------+-------+
                | register_service()
                v
      +--------+-------+
  +-->|    Offering    |
  |   | (周期广播Offer) |
  |   +--------+-------+
  |            |
  |            | unregister_service()
  |            v
  |   +--------+-------+
  +---|    Stopped     |
      | (已发TTL=0 Offer,|
      |  本地资源已清理) |
      +--------+-------+
               |
               | 本地清理完成（同步）
               v
      +--------+-------+
      |   NotOffered   |
      +----------------+
```

| 当前状态       | 事件                    | 下一状态       | 动作                     |
| ---------- | --------------------- | ---------- | ---------------------- |
| NotOffered | register\_service()   | Offering   | 开始周期广播 Offer           |
| Offering   | 收到 Find               | Offering   | 单播响应（格式同 Offer）        |
| Offering   | unregister\_service() | Stopped    | 发送 TTL=0 Offer 一次，停止广播 |
| Stopped    | 本地清理完成                | NotOffered | 清理本地资源                 |

**注册粒度为实例级**：状态机作用对象是 `(SvcID, InstID)` 实例。同一 `SvcID` 的多个 `InstID` 各自独立走该状态机，互不影响。

### 7.4 客户端视角 — 服务发现生命周期

```
            +----------------+
  +-------->|    Unknown     |
  |         | (未知服务状态) |
  |         +--------+-------+
  |                  | send Find / 收到 Offer
  |                  v
  |         +--------+-------+
  |         |     Found      |
  |   +-----|(已知服务,未订阅)|
  |   |     +--------+-------+
  |   | Offer 过期   | send Subscribe(CON) 收到 0x10 确认
  |   |              v
  |   |     +--------+-------+
  |   |     |   Subscribed   |
  |   |     |(已订阅,接收事件)|
  |   |     +--------+-------+
  |   |              | send Subscribe(TTL=0) 收到确认
  |   |              v
  |   |     +--------+-------+
  |   |     |  Unsubscribed  |
  |   |     |(已知服务,未订阅)|
  |   |     +--------+-------+
  |   |              | Offer TTL=0 / Offer 过期
  |   |              v
  |   |     +--------+-------+
  |   +---->|    Expired     |
  +---------| (服务不可用了) |
  重新Find  +--------+-------+
```

> 图中"重新Find"为重新发起发现流程的动作标注；Expired 收到 Offer(TTL>0) 直接回 Found（见下表）。

| 当前状态         | 事件                                        | 下一状态         | 动作                                                                              |
| ------------ | ----------------------------------------- | ------------ | ------------------------------------------------------------------------------- |
| Unknown      | 收到 Offer (TTL>0)                          | Found        | 按 (svc\_id,inst\_id) 加入注册表，启动 TTL 倒计时；若该实例存在未取消的订阅登记（见下方自动重订阅），随即自动发送 Subscribe |
| Unknown      | 主动 Find 收到响应                              | Found        | 同上                                                                              |
| Found        | 发送 Subscribe(CON)，收到 Code=0x10 确认         | Subscribed   | 记录订阅关系；随后的全量 Notification 按事件交付（数据分发，非确认信号，见 §8.1）                              |
| Found        | 等待确认期间收到事件推送                              | Found        | 容错：按事件交付（订阅实际已建立）；状态迁移仍由 0x10 确认驱动                                              |
| Found        | 收到 Offer(TTL>0)（常规刷新）                     | Found        | 刷新**实例发现缓存**的 TTL 倒计时（实例级维护，与订阅 TTL 无关，见 §7.5）                                  |
| Found        | Subscribe(CON) 收到 RST(0x20/0x24)          | Found        | 停止重传，释放会话 StrmID，向应用报订阅失败                                                       |
| Subscribed   | 收到事件推送                                    | Subscribed   | 交付应用层                                                                           |
| Subscribed   | 收到 Offer(TTL>0)（常规刷新）                     | Subscribed   | 刷新**实例发现缓存**的 TTL 倒计时（实例级维护，与订阅 TTL 无关，见 §7.5）                                  |
| Subscribed   | 发送 Subscribe(TTL=0)，收到传输确认 ACK(Code=0x00) | Unsubscribed | 移除本地订阅关系，释放会话 StrmID                                                            |
| Subscribed   | Subscribe(TTL=0) 收到 RST                   | Subscribed   | 停止重传，释放会话 StrmID（服务端订阅记录未删时靠订阅 TTL 自愈过期）                                        |
| Found        | Offer TTL 倒计时归零 / 收到 Offer(TTL=0)         | Expired      | 从注册表移除；取消确认等待定时器                                                                |
| Subscribed   | Offer TTL 倒计时归零 / 收到 Offer(TTL=0)         | Expired      | 从注册表移除，停止接收；**保留订阅登记（供自动重订阅）**                                                  |
| Unsubscribed | Offer TTL=0 或 Offer TTL 倒计时归零             | Expired      | 从注册表移除                                                                          |
| Expired      | 重新收到 Offer (TTL>0)                        | Found        | 重新加入注册表；见下方自动重订阅                                                                |
| Any          | 收到 REN=1                                  | Unknown      | 清除该节点（源地址）的所有实例缓存与订阅登记                                                          |

**自动重订阅**：实例 Expired→重新 Found 后，若应用层订阅登记仍存在，协议栈**自动发送 Subscribe**（新会话、新会话 StrmID——服务端订阅表在过期期间已删除该订阅者，按首次处理、回 0x10 确认并推全量，行为正确）；应用层 handle 持续有效，无需重新调用 `subscribe()`。重订阅期间服务再次消失 → 回 Expired，循环。**订阅登记的清除条件仅有二**：① 应用层显式 `unsubscribe`（应用实例析构/删除前应主动调用，见 §13.2）；② 收到对端 REN（§3.6：服务端重启后订阅表已全清，客户端登记同步清除，服务恢复后由应用重新订阅）。

状态机作用对象为**实例** `(SvcID, InstID)`；同一实例的多个 IfID 共享一条注册记录与一个 TTL 倒计时。Subscribed→Unsubscribed 仅由显式取消触发；实例失效（Offer 停止）统一走 Expired。

### 7.5 TTL 机制

**统一规则**：TTL=0（显式停止/取消）与 TTL 归零，都不立即删除条目，而是标记为待移除，在下一次 tick 时统一清理。

**条目状态**：

| state   | 含义   | tick 行为                    | 触发条件              |
| ------- | ---- | -------------------------- | ----------------- |
| Active  | 正常有效 | 剩余 TTL 递减 1；归零 → 转 Expired | 收到 TTL>0          |
| Expired | 待移除  | 在下一次 tick 时删除条目            | TTL 归零 / 收到 TTL=0 |

**发送方（Offer 广播 / Subscribe 保活）**：每 `period` 发送一次，Entry 中携带固定的 `ttl` 值，不递减。

**接收方（对端 Offer / 对端 Subscribe）**：

- 收到 TTL>0：剩余 TTL 置为 TTL，state = Active（重置而非累加）

- 收到 TTL=0：state = Expired

- 每秒 tick：按上表推进状态；Expired 条目在本次 tick 删除

- tick 固定 1s，不作为配置项：tick 粒度只影响已死条目的残留清理时长（最长 ttl + 1s），不影响正确性——误删条件仅取决于 `period < ttl`（周期性保活必然在 TTL 内刷新），与 tick 无关；TTL 归零后的实际清理延迟 ≤ 1s

Offer 与 Subscribe 两侧规则完全一致：客户端维护远端实例的 Offer TTL，服务端维护订阅者的 Subscribe TTL。客户端不维护订阅 TTL 计时：订阅失效的感知由 Offer TTL 覆盖（实例 Expired → 自动重订阅，见 §7.4），订阅静默失效的残余风险由 REN ×3 压至独立丢包率三次方量级。

### 7.6 SD 交互时序

```
场景1 主动发现:  客户端 --- SD Find ---> 服务端
                  客户端 <--- SD Offer --- 服务端

场景2 被动发现:  客户端 <--- SD Offer (周期组播) --- 服务端

场景3 订阅事件:  客户端 --- SD Subscribe (TTL>0, 首次 CON，会话 StrmID，周期 period) ---> 服务端 (单播)
                  客户端 <-- ACK(Code=0x10, 回显会话 StrmID) --- 服务端 (订阅建立确认，兼作传输层确认，有/无缓存一致)
                  （有缓存时随后推送全量 Notification —— 纯数据分发，非确认信号；丢失按接口 reliable 重传/尽力而为）
                  （0x10 丢失时：客户端重传 CON，服务端按重传判定重发 0x10，不重推全量）

场景4 取消订阅:  客户端 --- SD Subscribe(TTL=0, CON，同会话 StrmID) ---> 服务端 (单播)
                  客户端 <-- ACK(Code=0x00, 回显会话 StrmID) --- 服务端 (取消的传输层确认)
                  服务端置 Expired，延迟到下次 tick 移除订阅关系

场景5 服务停止:  客户端 <--- SD Offer(TTL=0, TYP=NON) --- 服务端
                  客户端置 Expired，延迟到 tick 检查移除
                  （若订阅登记存在，服务恢复后自动重订阅，见 §7.4）

场景6 节点重启:  客户端 <--- REN=1 (UDP 组播 ×3，间隔 ~100ms) --- 服务端
                  客户端按源地址清空该节点的所有实例缓存与订阅登记
                  客户端 <--- SD Offer --- 服务端 (重新发现)

场景7 查询IDL:   客户端 --- SD GetIDL(Code=0x04, StrmID=查询ID, TCP单播) ---> 服务端
                  客户端 <--- Code=0x11 (回显 StrmID, Payload=IDL JSON 全文) --- 服务端
                  （本地 IDL 库无该定义 / MajorVer 不匹配 → RST(0x24, 回显 StrmID)；Payload ≠3B → RST(0x20)）
                  （UDP 上收到 GetIDL → RST(0x00)，GetIDL 仅 TCP 单播；见 §7.2 GetIDL 语义）
```

## 8. 事件推送（Notifier）

### 8.1 订阅管理

- **收到 Subscribe**：TTL>0 时加入订阅列表/保活刷新（state=Active）；TTL=0 时置 Expired；订阅记录从无到有时推送全量数据（数据分发，见下）

- **GrpId 语义**：见 §7.1

- **订阅健康检查**：按 §7.5 状态机推进，Expired 条目在 tick 时删除

**全量推送**：服务端订阅记录**从无到有**时，直接推送接口缓存的最新数据（每条订阅仅一次）——**纯数据分发行为，不是订阅确认信号**。服务注册后应主动 `notify` 初始化缓存；后续数据变化时 `notify` 更新缓存并分发给所有订阅者。全量推送按接口 `reliable` 配置走 CON（重传保证送达）/ NON（尽力而为，丢失不重补）；需要可靠初始数据的应用应声明 `reliable: true`。

**订阅确认语义**：服务端对 **TYP=CON 的 Subscribe 一律回确认（无论首次还是重传到达，有/无缓存一致）**，客户端据此从 Found 进入 Subscribed：

| 到达帧                        | 服务端行为                                                                                        |
| -------------------------- | -------------------------------------------------------------------------------------------- |
| 首次 CON（TTL>0）              | 建立订阅 + 回 `CTR=1, TYP=ACK, Code=0x10`（订阅已建立，兼作传输确认）；若接口有缓存数据，**随后**推送全量 Notification（数据分发，见上） |
| **重复 CON（同会话 StrmID，即重传）** | **重发** **`ACK(Code=0x10)`，不重新执行、不重推全量**                                                      |
| 取消 CON（TTL=0）              | 置 Expired + 回空确认 `ACK(Code=0x00)`（取消的传输确认，见 §3.7）                                            |
| NON 保活（TTL>0）              | 刷新 TTL，不回任何确认                                                                                |

- 确认帧（0x10 / 0x00）**回显 Subscribe 会话的 StrmID**

- 客户端收到 0x10 → 取消该会话重传定时器，状态 Found→Subscribed；随后收到的全量 Notification 按事件正常交付（若在 0x10 前收到事件推送，按 §7.4 容错交付）

- 该设计保证：① **确认与数据解耦**——客户端状态迁移只依赖 0x10 单一信号，不依赖数据是否到达；② 确认帧在 UDP 上丢失时，客户端重传 CON → 服务端按重传判定重发 0x10 → 客户端最终进入 Subscribed（不存在永久卡死 Found 的路径）；③ 全量数据丢失由 `reliable` 配置决定恢复方式（CON 重传 / NON 尽力而为）

### 8.2 多客户端推送

- 按 `(svc_id, if_id, inst_id)` 查订阅者列表

- 每个客户端独立分配 StrmID，按需编码后逐个发送

- 每个客户端 ACK 独立匹配 `(peer, svc_id, inst_id, StrmID)`

- **transport=tcp 的 event 接口**：推送复用该客户端已建立的 TCP 连接（按订阅者源 IP 匹配活跃连接，TYP=NON；同 IP 多条连接时按实现策略选择）；订阅时无可用连接 → RST(0x24)（见 §7.2）；连接断开期间推送暂停（不补发），订阅记录保留，重连后自动恢复（见 §12.3）

- 客户端侧接收 CON Notification 需按 `(peer, svc_id, inst_id, StrmID)` 维护**接收记录**：传输 ACK 回答与重复帧去重共用该记录（重复 CON 到达仍须回 ACK，仅不重复交付应用）；记录保留至该 StrmID 冷却或 ≥ 重传窗口（3s）+ 单向延迟

## 9. 结构化数据字段

### 9.1 编码总则

- 字段按 IDL schema 的字段顺序**裸值连续编码**：无字段头、无类型标记、无结构边界标记、无 null/optional 标记。

- 所有多字节数值统一**大端序**。

- 类型、宽度、长度前缀宽度全部由 IDL 静态确定；解码端按 schema 顺序读取，不依赖任何线上类型信息。

- Payload 字节数由帧头 PLB/Length 承载（见 §3.1）。schema 字段序列解码完成后，剩余字节视为对端新增的末尾字段并忽略（见 §11.2）。

- 编码器必须按 IDL 声明的精确宽度输出；解码器读取每个字段前必须校验剩余字节足够，不足 → 解码失败（数据帧回 RST 0x20）。

### 9.2 类型编码

| IDL 类型 | 线上编码 | 字节数 | 说明 |
| ---------------------- | ------------------- | --------- | ---------------------------- |
| `u8` / `u16` / `u32` / `u64` | 无符号大端 | 1 / 2 / 4 / 8 | 编码/解码校验值域 |
| `i8` / `i16` / `i32` / `i64` | 二进制补码大端 | 1 / 2 / 4 / 8 | 编码/解码校验值域 |
| `f32` | IEEE754 单精度大端 | 4 | |
| `f64` | IEEE754 双精度大端 | 8 | |
| `f80` | x87 80bit 扩展精度大端 | 10 | 可选扩展：IDL 加载期校验本端支持，不支持则拒绝加载 |
| `bool` | `0x00`（false）/ `0x01`（true） | 1 | 其他值抛 `InvalidBoolEncoding` |
| `timestamp` | 48bit 无符号大端 | 6 | 自 2000-01-01 00:00:00 UTC 起的毫秒数，约 8925 年 |
| `enum` | 按 `base` 声明的整型裸值 | base 宽度 | 未知值透传（见 §11.2） |
| `struct` | 字段按 schema 顺序裸排 | Σ 字段宽度 | 无边界标记 |

**timestamp**：6B 大端无符号整数，值为自 2000-01-01 00:00:00 UTC 起的毫秒数。

**bool 严格解码**：仅 `0x00` / `0x01` 合法，其他字节抛 `InvalidBoolEncoding`。

**enum**：`base` 取 `u8/u16/u32/u64/i8/i16/i32/i64`，默认 `u8`；线格式即该基类型的裸值（有符号时补码）。负值仅在 `base` 为有符号类型时合法，编码/解码按 base 值域校验。

### 9.3 变长字段与长度前缀

**强制约束**：`string` / `bytes` / `array` 必须声明 `fixed_len` 或 `max_len` 之一；二者都缺 → **IDL 加载失败**（见 §11.1）——无上界则长度前缀宽度无法静态确定，解码端无法定位后续字段。

| 声明 | 长度前缀 | 内容 |
| ---------------- | ---------------- | ------------------------------------ |
| `fixed_len = N` | **无** | string/bytes：恰 N 字节；array：恰 N 个元素裸排 |
| `max_len = N` | `w(N)` 字节，值为实际长度/元素个数 | string/bytes：实际字节数 ≤ N；array：实际元素个数 ≤ N |

**长度前缀宽度 w(N)**（大端无符号）：

| max_len N | 前缀宽度 |
| ------------- | ---- |
| N ≤ 255 | 1B |
| N ≤ 65535 | 2B |
| N > 65535 | 4B |

- `string`：UTF-8 编码，长度值为**字节数**（非字符数）；空串长度 0。

- `bytes`：长度值为字节数；空 bytes 长度 0。

- `array`：长度值为**元素个数**（非字节数）；元素按 §9.2 / §9.4 逐个编码，元素无类型头。

- 编码校验：`fixed_len` 输入必须恰为 N；`max_len` 实际长度 ≤ N。解码校验：`fixed_len` 读出长度必须 == N；`max_len` 读出长度 ≤ N。违反 → 解码失败（数据帧回 RST 0x20）。

**定长空位填充**：`fixed_len` 对象由构造方实例化为恰好 N 字节 / N 元素后编码，编码器不自动补齐。空位默认值：

| 类型 | 空位默认值 |
| ------------------- | ---------------- |
| 整型（u*/i*/enum） | 0 |
| `bool` | `0x00` |
| `f32` / `f64` / `f80` | 0.0 |
| `timestamp` | 0（2000-01-01） |
| `string` / `bytes` | `0x00` 字节 |
| `struct` | 各字段取上述默认值 |

### 9.4 结构体、数组与嵌套

**结构体**：N 个字段按 schema 顺序裸排，无边界标记。

**数组**：

```
fixed_len = N:  [元素1][元素2]...[元素N]              // 无长度前缀
max_len = N:    [长度 w(N)][元素1]...[元素n]          // n ≤ N，长度为元素个数
```

**嵌套**：struct 可含 struct / array，array 元素可为 struct / array，支持多维数组。每层按自身声明处理：`fixed_len` 层无前缀，`max_len` 层有前缀；递归编码，无额外边界标记。

**多维定长数组**：`array<array<u8>, fixed_len=4>` 再 `fixed_len=3` → 12 字节裸排（3×4），各层均无前缀。

### 9.5 编码示例

| 字段 | 编码字节 | 说明 |
| ------------------------------- | ------------------- | -------- |
| `u8` 255 | `FF` | 1B |
| `u16` 4660 | `12 34` | 大端 |
| `i8` -128 | `80` | 补码 |
| `i16` -1 | `FF FF` | 补码 |
| `f32` 3.14159 | `40 49 0F D0` | IEEE754 大端 |
| `bool` true / false | `01` / `00` | |
| `timestamp` t=1 | `00 00 00 00 00 01` | 6B |
| `string` "hi"，`max_len=64` | `02 68 69` | 1B 前缀（64 ≤ 255） |
| `string` "abcd"，`fixed_len=4` | `61 62 63 64` | 无前缀 |
| `bytes` `[00,FF]`，`max_len=64` | `02 00 FF` | 1B 前缀 |
| `array<u8>` `[1,2]`，`max_len=100` | `02 01 02` | 1B 前缀（元素个数） |
| `array<u8>` `[1,2,3]`，`fixed_len=3` | `01 02 03` | 无前缀 |
| `struct{ u8, i8 }` 值 `{1,-1}` | `01 FF` | 字段裸排 |

### 9.6 CRC 校验

CRC 作为服务契约约定，**缺省关闭**：接口声明 `"crc": true` 时启用，否则不附加。CRC 校验由契约级编解码负责，通用帧解析层不感知 CRC 存在与否（见 §4.3）。

**唯一变体：CRC-16/CCITT-FALSE**：

| 参数 | 值 |
| ---------------- | ------------------------------------------------- |
| 多项式（poly） | 0x1021 |
| 初值（init） | 0xFFFF |
| 输入反射（refin） | false |
| 输出反射（refout） | false |
| 输出异或（xorout） | 0x0000 |
| 标准校验值 | `CRC-16/CCITT-FALSE("123456789") = 0x29B1`（实现自检用） |

**附加规则**：

- 2 字节结果**大端**附加于字段序列末尾，计入 Payload Length。

- **仅数据帧（CTR=0）可附加 CRC**；控制帧（CTR=1）不附加 CRC。

- 与 MSK 的顺序（见 §10）：先计算并附加 CRC，再对整体（字段序列 + CRC）应用 MSK XOR。

- 接收方处理顺序：**XOR 还原 → 取末尾 2 字节 CRC 校验（不匹配按 0x20 Bad Request 处理）→ 剥离 CRC → 按 §9.2~§9.4 解码字段**。

**裸字节编码下 CRC 的作用**：类型/宽度错配无法由线上类型标记发现；启用 CRC 时校验失败即报 0x20，是唯一的契约错配探测手段。关键接口应开启。

## 10. MSK 掩码机制

MSK=1 时，Payload Length 后插入 4B Masking Key，对 Data Fields 逐字节循环 XOR：

```
encoded[i] = payload[i] XOR maskingKey[i % 4]
```

- 每帧随机生成 4B Key；仅 XOR Data Fields（帧头与 Length 不处理），编解码对称

- MSK=0 明文传输

- **仅数据帧（CTR=0）可使用 MSK**：控制帧（CTR=1）固定 MSK=0（协议栈内部帧无混淆需求，跨实现硬性约定）；控制帧 MSK=1 属协议违规 → RST(0x00)（见 §4.3 步骤 1）

- **用途**：规避中间设备对载荷的误识别；**不是加密机制**，安全保证由环境层提供（见 §2）

- **CRC 与 MSK 顺序**：先算 CRC16 附加在 Data 末尾，再对整体（Data + CRC）应用 MSK XOR

| `svc_id` | 服务标识，全局唯一，各节点共享同一份 IDL；十进制字面量 |
| `if_id` | 接口标识，同一服务内唯一。1~~32767（0x0001~~0x7FFF）用于 rpc/ff，32768~~65535（0x8000~~0xFFFF）用于 event |
| `type` | `rpc`（请求-响应）、`ff`（无响应调用）、`event`（事件推送） |
| `transport` | 传输协议绑定，一律小写：`"tcp"` 或 `"udp"`，省略时按类型默认（rpc/ff=tcp，event=udp） |
| `max_payload` | **接口级**单帧 Payload 字节上限（TCP/UDP 均适用）。UDP 接口受 `max_payload_len`（1400）双重约束；TCP 大数据接口在此声明实际上限（如 1048576）。与字段级 `max_len` 同名不同义 |
| `reliable` | event 接口推送可靠性：`true`=UDP 上走 TYP=CON（需 ACK 重传）；`false`/省略=TYP=NON 尽力投递。TCP 接口恒为 NON |
| `crc` | 接口级布尔声明（默认 `false`）：`true` 时 payload 末尾附加 2B CRC16（见 §9.6）；控制帧不附加 |
| `input` / `output` | 参数/返回值类型，引用 `structs` / `arrays` / `enums` 中定义的类型名 |
| `fixed_len` | 定长：string/bytes 的字节数、array 的元素个数。**无长度前缀**，内容/元素裸排恰为 N（见 §9.3） |
| `max_len` | **字段级**变长上限：string/bytes 的字节数、array 的元素个数。**有长度前缀**，宽度按 N 静态推导（见 §9.3）；`string`/`bytes`/`array` 必须声明 `fixed_len` 或 `max_len` 之一，二者都缺 → IDL 加载失败 |
| `element_type` | 数组元素类型，可为标量、`struct` 或 `array`（支持任意嵌套，见 §9.4） |
| `grp_id` / `members` | 服务内 8bit 组号（1\~255）与该组包含的 event `if_id` 列表（见 §7.1） |
| `base` | enum 基类型：`u8`/`u16`/`u32`/`u64`/`i8`/`i16`/`i32`/`i64`，默认 `u8`；有符号基类型允许负值（见 §9.2） |
| `values` | enum 名称到整数的映射；值必须在 `base` 值域内且互不重复，未知值透传（见 §11.2） |

**标量类型白名单**（字段 `type` / `element_type` 取值）：

| 类型 | 宽度 | 说明 |
| ------------------------- | ---- | ------------------ |
| `u8` / `u16` / `u32` / `u64` | 1/2/4/8 | 无符号 |
| `i8` / `i16` / `i32` / `i64` | 1/2/4/8 | 有符号补码 |
| `f32` / `f64` | 4/8 | IEEE754 |
| `f80` | 10 | x87 可选扩展（IDL 加载期校验） |
| `bool` | 1 | `0x00` / `0x01` |
| `timestamp` | 6 | 48bit 毫秒（2000 基准） |
| `string` / `bytes` | 变长 | 必须声明 `fixed_len` 或 `max_len` |
| `array` | 变长 | 必须声明 `fixed_len` 或 `max_len` |
| `struct` / `enum` 类型名 | 由定义决定 | 引用 `structs` / `enums` / `arrays` 中的定义 |

> 类型独立化后不存在 `size` / `width` 属性，也不存在 `optional`：全部字段必填，无 null 编码。

**类型定义的三处位置**：`structs`（结构体）、`arrays`（数组类型）、`enums`（枚举），均可在 `input`/`output`/`element_type` 中被引用，支持任意层级嵌套。

`inst_id` 由运行时注册服务时提供，不在 IDL 中声明。`(SvcID, InstID)` 的跨节点唯一性属部署规划问题，不在协议与 IDL 职责范围内（见 §3.5）。

`transport` 绑定声明内嵌于 IDL JSON（`interfaces[].transport` 字段），协议栈运行时解析用于路由（rpc/ff 与 event 的传输选择，见 §3.8/§7.2）——无代码生成、无 Stub：编解码由协议栈按已加载的 IDL 动态执行。

**纯动态架构：IDL 运行时加载（协议要求）**：

- **协议栈程序不内置任何 IDL**：全部服务定义在运行时加载，由此支持服务热插拔（增减服务无需重新编译/重启协议栈）

- **IDL 库（本地文件夹）**：协议栈从本地 IDL 库（文件夹形式，路径与文件命名为实现约定）加载 IDL JSON 文档；库内按 `(SvcID, MajorVer)` 组织；**解析失败的文件跳过并记 Error 日志，不阻塞其他服务加载**（启动健壮性）

- **服务端侧**：`register_service` 要求该 `svc_id` 的 IDL 在库中——**本地缺失时协议栈自动经 GetIDL 从集群在线实例拉取**（与客户端按需拉取同一机制，见 §7.2），拉取落盘后注册继续；无在线实例则注册失败。服务热插拔 = IDL 定义就绪 + 应用注册/注销 handler，协议栈状态机随之迁移（§7.5）

- **客户端侧按需拉取**：应用请求需要编解码的 SvcID 不在本地 IDL 库时，若 SD 发现缓存存在该服务在线实例，协议栈**自动发起 GetIDL**（见 §7.2）→ 拉取结果**持久化写入 IDL 库**（文件形式，重启后本地命中不重复拉取）→ 解析加载 → 继续编解码；发现缓存无在线实例则直接失败，不发起查询

- **拉取校验**：响应 JSON 自含 `svc_id`/`major_ver`，落盘前须与请求 Entry 一致，不一致按查询失败处理（IDL 库状态不变）

- **一致性要求**：拉取落盘与本地命中不重复查询均为一致性判定项（测试用例 5.28/5.29）

### 11.2 版本兼容规则

| 变更类型                 | MajorVersion | MinorVersion | 兼容性  |
| -------------------- | ------------ | ------------ | ---- |
| 新增字段（末尾，既有类型）        | 不变           | +1           | 向后兼容 |
| 删除字段                 | +1           | 0            | 不兼容  |
| 修改字段类型/宽度            | +1           | 0            | 不兼容  |
| 修改长度声明（fixed_len ↔ max_len 或上限变小） | +1 | 0 | 不兼容 |
| 新增接口                 | 不变           | +1           | 向后兼容 |
| 删除接口                 | +1           | 0            | 不兼容  |
| 新增 IDL 类型             | +1           | 0            | 不兼容  |

**Minor 向后兼容的实现前提**：

- 末尾新增字段的兼容性由解码算法保证：schema 字段耗尽后忽略剩余字节（见 §9.1），旧解码器天然不解析新字段

- 新增字段只能使用**既有类型名**；新增 IDL 类型（如新增宽度整型）属 Major 不兼容变更——旧解码器无对应宽度，无法定界跳过

- **enum 未知值透传**：MinorVer 新增枚举值时，旧解码器按 base 整型保留原值交付应用，不报错（见 §9.2）

**服务版本匹配规则**：

- SD Offer 携带 MajorVersion + MinorVersion

- SD Find Entry 携带 MajorVersion（MinorVersion 不参与匹配）

- 仅 MajorVersion 精确匹配即视为服务兼容；MinorVersion 由客户端自行判断

- MajorVersion 不匹配 → 服务不可用，客户端不得发起调用

区分两个层级：**协议版本 VER（帧格式级，见 §2，双方必须相等）** 与 **服务版本 Major/Minor（接口语义级，见本节）**，两者独立演化。

## 12. 错误处理与恢复

### 12.1 错误码总表

| 错误码        | 名称                  | 触发条件                                                                                                                                                                                                                             | 恢复策略                                                   |
| ---------- | ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| 0x00       | Protocol Violation  | 帧头一致性校验失败（CTR/REN 组合非法、REN=1 时 TYP≠NON 或 Code≠0x00、ACK 时 Code∉{0x00, 0x10（仅 CTR=1，见 §8.1）}、ACK/RST 时 PLB>0、SvcID/IfID/InstID 越界、**控制帧 MSK=1**、**控制帧 StrmID 与 Code 语义不符**\[Subscribe/GetIDL 带 0x00、连接级帧带 0x01\~0x7F，见 §4.3 步骤 4]） | 丢弃帧，不响应（组播）；单播回 RST(0x00)                              |
| 0x20       | Bad Request         | Payload 字节序列与 IDL 契约不符（字段越界/截断、`bool` 非 `0x00`/`0x01`、`fixed_len` 长度不符、`max_len` 超限、`enum` 值超出 `base` 值域）、CRC 校验失败、控制帧格式错误（TCP/UDP 一致）                                                                                                                      | 应用层修正请求格式                                              |
| 0x21       | —                   | 保留                                                                                                                                                                                                                               | —                                                      |

| 0x23       | Payload Too Large   | Payload 超过 `max_payload_len`（仅 UDP，帧级校验；IDL 级超限归 0x20，见 §3.8/§9.3）                                                                                                                                                               | 减小 Payload 或改用 TCP 接口                                  |
| 0x24       | Not Found           | SvcID/IfID 无对应处理者                                                                                                                                                                                                                | 检查服务是否已注册/发现                                           |

| 0x26       | Frame Timeout       | TCP 半帧超时：帧头不完整（<8B）→ 关连接；帧头完整、Payload 不完整 → 丢弃恢复（见 §4.1）                                                                                                                                                                         | 发送端将本次请求/推送标记失败（不等响应、不再重传），机械发完当前帧剩余字节；接收端按 §4.1 两阶段处理 |

| 0x32       | —                   | 保留                                                                                                                                                                                                                               | —                                                      |
| 0x33       | Service Unavailable | 服务临时不可用（如过载）                                                                                                                                                                                                                     | 客户端退避重试                                                |
| 0x34\~0x3F | —                   | 保留                                                                                                                                                                                                                               | —                                                      |

### 12.2 控制帧错误

控制帧错误码仅用于 SD 单播交互（Subscribe 失败响应、GetIDL 查询失败响应）。组播 SD 操作（Offer/Find）不发送错误响应，不匹配时静默丢弃。

| 错误码  | 名称                  | 触发条件                                                                                                       | 恢复策略                                       |
| ---- | ------------------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| 0x20 | Bad Request (SD)    | SD 帧 Payload 整体无法解析；GetIDL 请求 Payload ≠ 3B（非 1×Entry）或 SvcID=0                                             | 回 RST(0x20)；单 Entry 无效不整帧拒绝（丢弃+日志，见 §7.2）  |
| 0x22 | Unsupported Version | VER 与本端不一致                                                                                                 | 忽略或记录日志（组播不回应）                             |
| 0x24 | Not Found (SD)      | Find 查询的服务/实例不存在；tcp-event 订阅时无该客户端 TCP 连接；GetIDL 查询时本地 IDL 库无该 (SvcID, MajorVer) 已加载定义（含从未部署/定义已卸载/版本不匹配） | 无（组播 Find 不强制回应）/ 订阅拒绝 / IDL 查询失败（均见 §7.2） |

### 12.3 传输层错误

| 场景                         | 检测方式                                    | 恢复策略                                                                        |
| -------------------------- | --------------------------------------- | --------------------------------------------------------------------------- |
| TCP 连接断开                   | 连接不可用                                   | 清理该连接的所有 Stream，通知应用层；tcp-event 订阅记录保留（推送暂停，见下行）                            |
| tcp-event 推送通道断开           | 订阅的 transport=tcp event 接口对应连接断开        | 订阅记录保留（按订阅 TTL 维护），推送暂停不补发；客户端重连后自动恢复（见 §7.2/§8.2）                          |
| TCP 半帧超时（帧头不完整，<8B）        | 帧开始接收后超过 tcp\_frame\_timeout\_ms 且帧头未收齐 | 回 RST(0x26) 后**关闭连接**（帧总长不可知，无法重同步）；客户端按 §5.6 自动重连                          |
| TCP 半帧超时（帧头完整、Payload 不完整） | 帧开始接收后超过 tcp\_frame\_timeout\_ms 且帧头已收齐 | 回 RST(0x26)，进入丢弃模式按帧头声明的帧总长精确丢弃剩余字节，收满后恢复正常接收，**连接不关闭继续复用**；退出条件与兜底超时见 §4.1 |
| UDP 报文丢失                   | 无检测（NON）或 ACK 超时（CON）                   | NON 不恢复；CON 重传至 max\_retry                                                  |
| 服务端 REN=1                  | 收到 REN 控制帧                              | 清空该节点服务缓存 + 该对端全部 Stream/重传记录，等待 SD Offer 重建                                |
| 响应超时（Request）              | 应用层定时器触发                                | 报应用层 RequestTimeout，同时取消该 StrmID 的待确认重传                                     |
| 重传耗尽（UDP CON）              | 末次后等待 1600ms                            | 静默停止重传，清理待确认记录，不报错；请求成败由响应超时判定                                              |
| 重传到达（服务端）                  | 收到相同 StrmID 的重复请求                       | 重发缓存响应，不重复执行处理逻辑                                                            |

### 12.4 日志格式

```
[{Timestamp}][{level}][{svc_id:04X},{if_id:04X},{inst_id:02X}] {Tx|Rx},{addr} {strm_id:02X}, Code=0x{code:02X}, Msg={msg}
```

其中 `Msg` 取 §12.1 / §12.2 中的错误码名称（如 `Not Found`、`Payload Too Large`）。

## 13. 公共 API 契约

以下为应用层接口的语义契约。具体签名与语言绑定由各实现决定。

> **payload 语义（纯动态架构）**：应用传入/接收的 `payload` 为按 IDL 定义的结构化字段值集合，编解码由协议栈按本地 IDL 库动态执行（见 §11.1）——应用不直接操作线格式字节；调用/订阅涉及的 SvcID 不在本地 IDL 库时，协议栈自动经 GetIDL 拉取（见 §7.2），对应用透明。

### 13.1 服务端

| 接口                                           | 语义                    | 前置条件                                                                                                                                     | 失败条件                                                                                                                 |
| -------------------------------------------- | --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `register_service(svc_id, inst_id, handler)` | 注册服务实例，进入 Offering 状态 | handler 覆盖该实例的全部 IfID；该 `svc_id` 的 IDL **在本地 IDL 库或可自动拉取**（本地缺失且发现缓存有在线实例时，协议栈自动 GetIDL 拉取落盘后继续注册，见 §7.2/§11.1；协议栈启动即发 Find 预热发现缓存，见 §2） | 本地 `(svc_id, inst_id)` 已被占用；IDL 库无该 `svc_id` 定义**且**无法自动拉取（集群无在线实例 / 拉取失败）——失败可由应用重试，发现缓存随启动 Find 与周期 Offer 更新后重试可成功 |
| `unregister_service(svc_id, inst_id)`        | 注销实例，停止 Offer 广播      | 实例已注册                                                                                                                                    | —                                                                                                                    |
| `notify(svc_id, inst_id, if_id, payload)`    | 更新接口缓存并推送给所有订阅者       | 实例已注册                                                                                                                                    | 实例未注册                                                                                                                |

### 13.2 客户端

| 接口                                                     | 语义                                                                                                                                                                                                  |
| ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `call(svc_id, inst_id, if_id, payload, timeout)`       | 同步调用，阻塞至收到响应或超时；`timeout` 缺省取全局默认，可逐次指定                                                                                                                                                             |
| `call_async(svc_id, inst_id, if_id, payload, timeout)` | 异步调用，立即返回；`timeout` 语义同 `call`                                                                                                                                                                      |
| `fire_forget(svc_id, inst_id, if_id, payload)`         | 无响应调用                                                                                                                                                                                               |
| `subscribe(svc_id, inst_id, if_id, grp_id, on_event)`  | 订阅事件；`if_id` 与 `grp_id` 二选一（整组订阅时 `if_id=0x0000`）；**返回订阅句柄** **`handle`**（供 `unsubscribe` 使用，关联一个订阅会话 StrmID，见 §7.2）。实例未 Found 时调用：登记订阅意图并立即返回 handle，实例 Found 后协议栈自动发起 Subscribe（与自动重订阅同机制，见 §7.4） |
| `unsubscribe(handle)`                                  | 取消订阅（内部发送 Subscribe(TTL=0)）。应用实例析构/删除前应主动调用，避免悬空订阅登记（登记清除条件见 §7.4）                                                                                                                                  |
| `is_available(svc_id, inst_id)`                        | 查询实例可用性（本地缓存状态）：注册表中存在该实例、TTL 处于 Active、VER 与本端相等                                                                                                                                                   |
| `find_service(svc_id, inst_id, timeout)`               | 主动发现（触发 SD Find，刷新本地缓存）；返回该实例的在线信息（源地址、版本），不返回接口列表（接口定义由协议栈按需经 GetIDL 自动拉取至 IDL 库，见 §7.2/§11.1，应用无感知）                                                                                               |

> **可选增强（事件静默超时提示）**：应用可为订阅会话启用可选的"静默超时"——超过 N 秒（建议 ≥ 2×period + ttl）未收到该订阅的任何事件时向应用回调提示，由应用决定 re-Find / re-subscribe。用于兜底"服务端重启 + REN 三发全丢"的残余失效场景（该场景下订阅登记保留，仍靠 TTL 过期 + 自动重订阅恢复，见 §7.4；若 REN 已到达则登记已清，需应用重新 subscribe；静默提示仅供应用层感知中断，协议栈不强制实现，亦不依赖客户端对 TTL 的计时，见 §7.5）。

### 13.3 服务端处理契约

| 接口                                                 | 语义                                         |
| -------------------------------------------------- | ------------------------------------------ |
| `on_request(if_id, payload)`                       | 处理 rpc 请求，返回响应字段序列或错误                      |
| `on_fire_forget(if_id, payload)`                   | 处理 ff 调用，无返回值                              |
| `push_policy()`                                    | 推送策略：OnChange（数据变化时推送）或 Periodic(ms)（周期推送） |
| `on_notification(svc_id, if_id, inst_id, payload)` | 客户端侧：处理收到的事件推送                             |
